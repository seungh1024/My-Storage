# 작업 요약 (문제-고민-선택-결과)

## 1) 상하위 이동 교차 시 경로 길이 초과

### 문제
- 하위 이동이 진행 중일 때 상위 이동이 오래된 상태를 기준으로 검증을 통과해, 실행 단계에서 `name_full_path` 길이 초과가 발생했다.

### 고민
- 요청 시점 검증만으로 충분한지
- `is_moving`만으로 충돌을 안정적으로 막을 수 있는지
- 인덱스/쿼리를 어떻게 구성해야 hot path에서 비용이 낮은지

### 선택
- 진행 상태 정본을 `folder_operation_state`로 분리했다.
- `(root_id, folder_id)` 복합 PK + `INSERT` 기반으로 중복 작업 자체를 차단했다.
- 상위 이동 검증에 하위 `ACTIVE MOVE`의 예약 최대 길이를 포함했다.
- 최대값 조회는 `ORDER BY ... LIMIT 1` 대신 `MAX(...)` 기반으로 정리했다.

### 결과
- 상/하위 이동 교차 상황에서 경로 길이 검증 누락 가능성을 줄였다.
- 중복 이동 요청은 충돌 예외로 일관되게 처리되도록 정리됐다.

---

## 2) create 시 moving 조상 예약 길이 갱신 비용

### 문제
- moving 조상 수만큼 단건 update가 발생해 I/O가 과도해질 수 있었다.

### 고민
- 검증만 하고 저장은 분리할지
- update를 모아 한 번에 반영할지

### 선택
- `validateMaxNamePathLengthAndReserveForCreate`에서 갱신 대상만 수집해 배치 update로 반영했다.
- 동일 폴더 ID는 최대값 기준으로 merge해 단조 증가 형태로 정리했다.

### 결과
- create 경로의 DB 왕복 횟수를 줄였고, 예약 길이 갱신 비용을 예측 가능하게 만들었다.

## 3) `is_moving` 제거와 상태 모델 일원화

### 문제
- `is_moving`은 루트만 표시해 사용자/운영 관점의 상태 표현이 제한적이고, 새 상태 테이블과 이중 관리가 발생했다.

### 고민
- 호환 목적으로 유지할지
- 완전히 제거하고 상태 테이블로만 운영할지

### 선택
- 이동 충돌/진행 상태 판단을 `folder_operation_state`로 일원화했다.
- 코드/테스트의 `is_moving` 의존 로직을 제거했다.

### 결과
- 상태 소스가 단일화되어 해석이 단순해졌고, 테스트도 현재 정책 기준으로 정리됐다.

---

## 4) 폴더 용량 갱신 방식 전환 (이벤트 -> 트랜잭션 내 배치)

### 문제
- 폴더 용량을 이벤트 비동기로 반영할 때, 재시도/지연/오래된 메시지 소비로 운영 잡음이 있었다.

### 고민
- 이동/생성/파일이동 시점에 즉시 반영할지
- 이벤트 전파를 유지할지

### 선택
- 경로 기반 조상 ID를 계산해 델타를 합산하고, 트랜잭션 내에서 배치 update로 즉시 반영하도록 변경했다.
- `FolderSizeAdjustmentService` + `FolderMetadataRepository.batchUpdateSizeDeltas` 경로로 통합했다.

### 결과
- 용량 반영 타이밍이 요청 트랜잭션으로 수렴되어 일관성이 높아졌다.
- 이동/파일 이동/파일 생성 경로에서 동일한 델타 반영 패턴을 재사용하게 됐다.

## 5) 테스트/CI 안정화 과정

### 문제
- `NoClassDefFoundError`, Testcontainers 초기화 실패, Docker API 버전 이슈, 중복/불필요 스텁 등으로 CI 실패가 반복됐다.

### 고민
- 인프라 이슈와 비즈니스 로직 변경을 분리해서 봐야 하는지
- 동시성 테스트 강도를 어떻게 높일지

### 선택
- 테스트 초기화/의존성/스텁을 정리하고, 중복 케이스를 통합했다.
- 동시성 테스트는 고정 시나리오 대신 랜덤 이동 + 정합성 검증으로 강화했다.

### 결과
- 테스트가 현재 정책(`folder_operation_state`/배치 용량 반영)에 맞게 정렬됐다.
- 동시성 테스트가 “실제 이동 다양성”을 더 반영하도록 개선됐다.

## 6) move 충돌 정책 재정의 (하위 허용 -> 상/하위 전면 차단)

### 문제
- 기존에는 하위 이동 작업이 있어도 예약 최대 길이 비교로 상위 이동을 일부 허용했다.
- 이 방식은 검증/실행 시차가 있을 때 정책이 복잡해지고, 실제 운영에서 원인 파악이 어려웠다.

### 고민
- 하위 이동이 있을 때 길이 비교로 허용을 유지할지
- 한 서브트리 내 move를 1개로 강제해 정책을 단순화할지

### 선택
- `move vs move`는 상/하위 모두 차단으로 단순화했다.
  - 상위 경로(`source/target` 조상)에 operation state가 있으면 차단.
  - `source` 서브트리 하위에 ACTIVE move가 있으면 차단.
- 상위 충돌 검증은 `getFolderJobLock` 이전에 수행하도록 순서를 정리했다.

### 결과
- 한 서브트리 내 동시 move 허용 여지를 제거해 정책 해석이 단순해졌다.
- DFS 실행 중 교차 move로 인한 path 갱신 혼선 가능성을 구조적으로 줄였다.

## 7) create projected path 계산 단순화 + 단건 상태 갱신

### 문제
- create에서 moving 조상 반영 로직이 중복되고, 결과 객체가 중첩되어 호출부 가독성이 낮았다.

### 고민
- util에서 DB 갱신까지 처리할지
- 계산 결과만 반환하고 service에서 저장/갱신을 수행할지
- 결과 객체를 중첩 record로 유지할지 평탄화할지

### 선택
- `validateAndResolveForCreate`로 검증/경로 계산을 통합하고, 저장 책임은 service에 유지했다.
- moving 조상은 단건 조회로 강제하고, 다건이면 예외 처리했다.
- projected 경로 계산은 `id_full_path` 토큰에서 moving root id 인덱스를 기준으로 suffix를 절단/재조합하는 방식으로 고정했다.
- create 성공 시 moving 조상의 projected max 값이 함께 갱신되도록 반영했다.

### 결과
- create 흐름이 "검증/계산 -> 저장 -> 필요 시 단건 갱신"으로 명확해졌다.
- 단건 전제와 코드 구조가 일치해 디버깅/테스트 난이도가 낮아졌다.

## 8) 경계 조건/테스트 정합성 보정

### 문제
- `maxPathLength=250`에서 `>=` 비교는 길이 250 자체를 실패시켰다.
- move 검증 순서 변경 이후 일부 테스트가 기존 기대(`no interaction`, `unused stubbing`)로 실패했다.

### 고민
- 경계값을 250 허용으로 볼지
- 테스트를 기존 호출 순서에 맞출지, 새 정책 순서에 맞출지

### 선택
- 길이 비교를 `> maxPathLength` 기준으로 통일했다.
- 테스트 기대를 새 정책 순서에 맞게 수정했다.
  - path-too-long 케이스: `validateParentsUtil` 호출 1회 기대.
  - validateParentsUtil에서 예외가 나는 케이스: 불필요한 job lock stubbing 제거.

### 결과
- 경계값 동작이 정책(250 허용)과 일치하게 정리됐다.
- move 검증 순서 변경 후 테스트 실패 원인이 제거됐다.

## 9) 추가 정리: path 기반 동시성 이슈에서의 최종 선택

### move에서의 실제 쟁점
- 길이 초과 자체보다, 상/하위 move 교차 시 어떤 prefix가 최종 반영되는지 불명확해지는 문제가 더 컸다.
- `projectedMaxNamePathLength`는 길이 상한 관리에는 유효하지만, prefix 정합성 자체를 보장하지는 못했다.

### create에서의 실제 쟁점
- 상위 moving 작업이 여러 개일 수 있는 상태에서는 어떤 기준 경로를 선택해 길이 검증해야 하는지가 불명확했다.
- "상위 max projected 값" 기준 검증은 실제 create parent 기준 최종 경로를 보장하지 못했다.
- DFS+batch 구조상 부모 경로를 고정한 채 create를 처리하기 어려웠다.

### 고민
- create를 막고 move 완료를 기다릴지,
- create를 허용하되 실제 예상 parent 경로를 재구성해서 검증할지.
- create가 move보다 고빈도/경량이라는 점을 운영 정책에 반영할지.

### 최종 선택
- move: 한 서브트리에서 동시 1건만 허용(상/하위 move 전면 차단).
- create: 차단하지 않고, `operation_state`의 이동 루트 기준으로 parent 예상 경로를 재구성해 길이를 직접 검증.
- create 성공 시 해당 moving 작업의 projected max 값을 갱신해 이후 DFS 단계의 길이 초과 위험을 줄임.

### 결과
- move 충돌 정책은 단순해졌고 prefix 해석 모호성이 줄었다.
- create는 처리량을 유지하면서도, "max 추정"이 아닌 "실제 예상 경로" 기준으로 검증 정확도를 확보했다.

## 10) 상세 원인 분석: 왜 create에서 `name_full_path` 초과가 발생했는가

### 핵심 오해
- `operation_state`를 조회했다는 사실만으로, create의 최종 경로 길이가 항상 안전해지는 것은 아니다.
- `projectedMaxNamePathLength`는 길이 상한 관리 지표이지, 개별 create 대상 parent의 최종 prefix를 직접 보장하지 않는다.

### 실제 발생 조건
- create 검증 시점과 DFS 갱신 시점이 분리되어 있었다(TOCTOU).
- create는 통과했지만, 이후 DFS가 적용한 실제 최종 prefix가 더 길어져 런타임 update에서 초과가 발생할 수 있었다.
- create 타이밍에 생성된 노드가 해당 DFS 사이클의 부모 기반 순회에서 누락되면, 이동 반영이 늦어질 수 있었다.
- 이 상태에서 prefix 기반 max 조회가 과소평가되면, 다음 작업 검증이 안전하지 않은 값으로 통과할 수 있었다.

### 왜 max 기반만으로 부족했는가
- 상위 moving 작업이 여러 개일 수 있는 구간에서는 어떤 경로를 기준으로 검증할지 불명확했다.
- "상위 max projected의 최대값"은 보수적 지표일 수는 있어도, create 대상 parent의 실제 최종 경로를 항상 정확히 대변하지 못했다.

### 보완 결정
- move는 서브트리 내 1건만 허용해 교차 갱신 가능성을 제거했다.
- create는 `operation_state`의 이동 루트 기준으로 parent 예상 경로를 재구성해 직접 길이를 계산한다.
- create 성공 시 해당 move의 projected max를 즉시 갱신해 이후 검증/실행 불일치를 줄인다.

### 요약
- 문제의 본질은 "조회 누락" 단일 원인이 아니라,
  "검증 모델의 과소평가 가능성 + DFS/create 타이밍 불일치"의 결합이었다.
- 따라서 해결도 단일 max 비교가 아니라, 정책 단순화(move 1건) + 경로 재구성 검증(create)의 조합이 필요했다.
